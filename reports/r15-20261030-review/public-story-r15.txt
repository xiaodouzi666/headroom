  - heading "Inspiration" [level=2]
  - paragraph:
    - text: Every PyTorch engineer has met
    - code: torch.OutOfMemoryError
    - text: "at 3 a.m. PyTorch can record allocations with their call stacks, but large snapshots are difficult to inspect line by line. Nemotron 3 Ultra's long-input capability on Token Factory made an evidence-driven workflow practical for this project: give the model a snapshot-derived evidence pack, ask it to explain the peak, and test its proposed fix on the hardware."
  - heading "What it does" [level=2]
  - paragraph: Headroom runs your script on a real GPU with allocator history on, captures the memory snapshot at the point of failure, and sends a token-budgeted evidence pack — peak composition by call stack, hot allocation paths, fragmentation indicators, timeline and source — to Nemotron 3 Ultra for root-cause diagnosis. Nemotron 3 Super writes the patch as exact line edits; Headroom applies it, re-runs the script under the same seed, and keeps a result that meets the selected memory and numerical policy without shrinking the model or shortening training. It searches keep-or-revert for up to six rounds toward your memory target and records the PyTorch documentation consulted through Tavily.

  - heading "How we built it" [level=2]
  - list:
    - strong: "Lab:"
    - text: Docker-isolated runner (no network, read-only source),
    - code: torch.cuda.memory._record_memory_history
    - text: ", optimizer-step hooks for step counting and loss capture, same-seed re-runs, parameter-count and training-length checks."
    - strong: "Evidence pack:"
    - text: a restricted snapshot reader groups allocations by stack, reconstructs allocator history and prepares a token-budgeted representation.
    - strong: "Models on Nebius Token Factory:"
    - text: Nemotron 3 Ultra for diagnosis and planning, Nemotron 3 Super for structured line-edit patches and the Tavily tool loop, and Nemotron 3 Nano for optional stack labelling.
    - strong: "Measured input handling:"
    - text: Ultra accepted
    - strong: 268,920 input tokens
    - text: in an authentic evidence request and
    - strong: 500,029 input tokens
    - text: in a retrieval probe.
    - strong: "Verification and search:"
    - text: keep-or-revert rounds with per-round verification feedback sent back to the planner.
    - strong: "App:"
    - text: FastAPI + SSE backend and React front end with a live timeline, memory charts, diagnosis cards with clickable evidence stacks, diff and validation views, and a public gallery of historical cases.
  - heading "Challenges we ran into" [level=2]
  - paragraph: "Getting patches to apply was harder than producing a plausible diagnosis: malformed or truncated unified diffs led us to exact line edits bound to the original file hash, with structured error feedback. Verification needs care — a patch can appear to save memory by shrinking the model, skipping steps or changing the objective. Headroom checks parameter counts, update counts and loss series, and records when workload pairing is incomplete. Measuring and limiting long-input model use within a small credit allowance was another engineering task."
  - heading "Accomplishments that we're proud of" [level=2]
  - paragraph: Real repairs produced end to end by open models and tested on hardware; diagnoses tied to captured allocation stacks; a result history that preserves failed attempts alongside measured improvements; and an open-source project with a public results site.
  - heading "What we learned" [level=2]
  - paragraph: "Large context is useful when the evidence format is explicit and the model must cite recorded stack IDs. A valid JSON response is only the first step: diagnosis references, patch application and numerical comparisons need separate checks. Exact line edits made patch failures easier to explain and repair. The hardest part of an automatic optimization loop is deciding what the measurements actually support."
  - heading "What's next" [level=2]
  - paragraph: Improve strategy selection, evidence requests and malformed responses exposed by the latest suite; obtain successful precision-policy comparisons; extend diagnosis to FSDP/DeepSpeed workloads; and evaluate longer training runs.
  - heading "Limitations" [level=2]
  - paragraph: Historical memory-target successes come from separate runs and do not establish identical full-training behaviour. Numerical coverage varies by case, as detailed above and in RESULTS. The latest October 30 evaluation met one of nine memory targets, below the target of six; its raw first-category matches and valid correct diagnoses are reported separately. The diagnosis-only comparison is one fixed-order pass without repeats, with two unconfirmed reference causes retained in the full denominator. Both new s2 precision-policy tests and the HF Trainer repair failed to meet their requirements; a statically accepted HF configuration edit did not establish a successful repair. Saved-snapshot analysis has produced valid diagnoses, although some explanations still contain factual errors. The web interface can analyze an explicitly shared server capture by ID using new Nebius inference; external snapshot upload is optional. Neither path runs the supplied training code or proves a GPU repair. A large public upload timed out before analysis.
