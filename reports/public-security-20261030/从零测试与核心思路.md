## 1. 我们开发的是什么

Headroom 是给 PyTorch 训练脚本做显存诊断和自动修复的工具。它尝试回答三个问题：显存主要用在哪里；为什么发生 OOM（显存不足）或存在浪费；改完以后，是否真的省显存、且没有靠缩小模型或少训练几步冒充成功。

处理链条是：

网页选择示例或粘贴脚本 → azuki 上的 GPU 实际运行并采样 → 整理显存快照、调用栈、代码和训练记录 → 通过 Nebius Token Factory 调用 NVIDIA Nemotron 模型诊断并生成补丁 → azuki GPU 再运行候选脚本 → 比较显存、loss、参数量及配对条件 → 输出结果和可下载补丁。

azuki 的 GPU 主要用于运行被检查的训练代码、采集数据和复测。**Nebius 客户端是连接远程模型服务的程序，不是我们在 azuki 上部署了 Nemotron 大模型。** Nemotron Ultra 主要负责诊断与修复计划，Super 负责代码修改，Nano 可用于简短调用栈标签。具体任务是否调用某个模型、调用了几次，以该任务真实记录为准。Tavily 可用于查询相关文档，不是每个任务都必然搜索。

源代码会作为诊断上下文发送给 Nebius。不要向演示站点提交包含个人 API key、密码、私密训练数据或不应外发代码的脚本。这里只接受演示范围内的单文件 Python 输入，依赖和操作受现有镜像、静态检查及容器沙箱限制；任务内不能联网安装包。

## 2. “Mock”、示例和真实运行有什么区别

Mock 是开发测试里替代真实外部服务的假对象。例如，让一个假模型立即返回固定 JSON，用来检查“收到错误时按钮是否禁用”“无效令牌是否被拒绝”。这类测试不调用 Nebius、不占 GPU，也不能证明 AI 会修复代码。

网页里的预置示例，是我们设计的故障测试脚本或合成工作负载，并非随机收集的用户项目。**当你在恢复后的网页真正提交一个示例时，它仍然会在真实 GPU 上运行，也可能发起真实 Nebius 请求。** 不能因为它是“示例”就叫它 Mock，也不能凭示例成功推断任意真实项目都能修好。

Verified runs 展示过去真实运行的证据；只读打开不会重新执行任务。Results 展示汇总和失败边界。两者都不是 Replay 动画；本项目不再提供用户要求删除的 Replay。

## 7. 新思路目前到底实现到哪里

已经实现的是 **修复适用范围记录与查询 CLI**，文档在 [REPAIR_SCOPE.md](../../docs/REPAIR_SCOPE.md)。它把补丁、原始代码、输入、精度、设备、环境、策略和既有验证证据绑定起来，回答：

“这个确切补丁，在这个确切上下文里，是否有已记录的通过证据？”

它能返回 tested_pass、tested_fail、unknown、invalid_evidence。换了输入、精度、硬件或代码，不应沿用旧成功标签；有失败证据也不能只挑成功记录。该工具只读既有证据，不会自动跑实验、不会发模型请求，也不是前端 Replay。

**尚未实现主动边界发现**：不会自动改变 batch、输入长度、设备或精度并寻找全部失效边界。现有记录也不能证明一个连续安全区间或任意未来运行一定成功；不能宣称这是完全没人做过的研究成果。

Pareto/多配置搜索和允许精度变化的路径已有代码，但真实成功成果有限；两个额外 s2 精度策略实测没有通过，不能展示不存在的成功性能取舍。Snapshot 的两次 CLI 实测没有得到可用诊断，Web 上传也没有产出通过的修复；Watch 确实捕捉到 CUDA OOM 并尝试修复，但该次修复失败。它们的代码存在和真实成功是两件事。

## 8. 怎么判断本轮是否测试完了

至少保留这些记录：只读页面能否打开；一个新任务 ID；这次真实时间线；原始/候选显存与数值对比；实际 patch；报告下载结果；失败时的明确原因；令牌刷新后是否消失。没有提交新任务，就只写“只读页面测试完成”；只有离线假对象测试通过，就写“离线功能检查通过”。

安全说明同样保留边界：我们已定位并正在处理上传与输出存储的资源风险；Torch 2.5.1 仍有已知上游反序列化漏洞，当前源码未发现匿名上传checkpoint到host torch.load的直接入口，但这不等于整个服务已被证明无漏洞。详见 [依赖审计](../public-dependency-audit-20261030/README.md)。最终恢复前还需要审查和验证新的存储隔离实现。公网启动器新增并发上限 64、连接等待队列 64、空闲 keep-alive 5 秒；上传还有 3 个槽位和 30 秒总期限。这些是资源消耗保护，不是完整 DDoS 防护，也不能保证任意慢连接都不会影响可用性。
