## Scope and budget traps to avoid

1. The general scenario_set_v2.yaml has **12 rows**. Calling the full manifest with both policies selects 24 cases unless the caller applies the 10-case Phase 2 scope. protocol_plan builds the intended scope; run_campaign supports explicit scenario_ids, and the CLI supports repeated --scenario selections. The two library cases remain separate; HF is already in the ten-case core.
2. The primary MVP driver selects strict only. strict and allow_precision outcomes cannot be merged to make the 6/9 numerator. default continues to mean strict. The approved new matrix supersedes the old default/strict ambiguity prospectively; it does not rescore history.
3. The original Phase 2 $12 value is a ceiling, not a new account balance or authorization to create a $12 pool. All later work stays in the same authoritative gifted-credit ledger and existing approved allocation. Fresh ledger state and complete request upper bounds govern each dispatch. Do not free historical unknown charges, reset the ledger/day, borrow the judging reserve or recharge to finish a table.
4. A temporary MockTransport ledger used by offline tests is not the production budget. Keep its test receipts separate; production calls continue using the same actual ledger.
5. The latest strict full-suite result must be bound to current production/config/test/prompt sources. Focused test totals, old frontend checks and the S1/S2 human controls do not replace that receipt.
6. If a gate remains unmet, record the actual failure and continue independent already-authorized work. No repeated permission question is needed for existing gift-only model calls. A genuine budget boundary, external access requirement or change to the user's remaining objective is a separate decision, not something to hide by relaxing the gate.
