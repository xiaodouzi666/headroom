# 2026-10-27 开发交付：修复适用范围与费用小计

本轮完成一项独立功能和一项报告修复，未新增自动修复成绩。原 R3 仍为
目标 **3/9**、有效首因 **4/9**，低于保留的两项 6/9 门槛。
没有充值、没有新增付费模型调用，也没有清除 HTTP 529 对应的未知费用阻断。

## 新功能能做什么

新增命令 `headroom scope build` / `headroom scope check`，把明确选择的历史
修复轮次绑定到源码、补丁、输入/初始参数指纹、更新结构、精度、策略和已记录的
GPU/软件环境字段。查询前重新检查底层文件和补丁应用关系。

返回四种状态：已测通过、已测失败、未知、证据无效。同条件的失败不会被成功
覆盖；缺测量不是失败，也不是通过；没有测试过的配置不做插值或外推。
它是独立 CLI 功能，没有恢复前端 Replay，也没有改变自动修复器的原验收规则。

实际实现与使用方式：[REPAIR_SCOPE.md](../../docs/REPAIR_SCOPE.md)。
关键实现为 `headroom/verify/applicability.py`，并接入已有 CLI。

## 这是不是完全没人做过

不能这样保证。[一手先例核查](prior-art.md)记录了 8 项相关工作，包括自动
显存优化、编译条件检查，以及 CertiPatch 的带范围经验性证据。因此，本轮提供
GPU 内存修复领域的实用组合能力，不能称为世界首创或已经优于现有系统。

下一步更有研究价值的方向是主动寻找修复失效条件，再用预先固定的实验设计
比较它是否减少错误复用。这一“主动发现”尚未实现，不能与当前查询功能混淆。

## 实测与验证

既有 R3 s3 round 2 在其原有精确条件下被重新核查为 `tested_pass`，保留原来的
73.378694% 峰值下降。它是历史检查，没有再次执行，更没有算作新修复成功。

另用已知人工 no-grad 补丁执行了三对小规模 CUDA 控制，共 6 次目标执行。
每次 20 步，三个配对均保留相同输入、有效 batch、目标及相同 scalar loss。
预先固定的显存下降门槛是 20%，结果全部未达标并被保留为失败：

| tiny 模型的 eval batch | 原峰值 GB | 修复后 GB | 下降 | 20% 目标 |
|---|---:|---:|---:|---|
| 2 | 0.068344832 | 0.068316160 | 0.041952% | 未达标 |
| 16 | 0.068647424 | 0.068432384 | 0.313253% | 未达标 |
| 64 | 0.069691904 | 0.068831744 | 1.234232% | 未达标 |

这些是 `human_control`，不是模型生成补丁的成功率测试。tiny 选项也改变模型
宽度、深度及序列长度，所以不能把它与旧 R3 的差异归因于单一 batch 因素。
这些控制说明需要保留条件，未证明优化普遍有效或无效。

实用查询验证：原 s3 点返回通过；三个控制点返回失败；未测 GPU 返回未知；
从记录中删除一个观察而保留原选择索引，检查返回证据无效。没有把未执行的
GPU 配置说成测过。[实际查询凭据](scope-verification.json)、
[控制执行凭据](gpu-controls-evidence.json)、[范围记录](scope.json)。

## 费用汇总修复

R3 内部有已知费用，但部分行的实际总额未知，旧汇总把这些已知小计漏掉。
现在 campaign、policy 与公开结果都保留已知小计，且不把保留额度当成实际消费。

重新读取原 R3 数据得到已知小计 **$1.20596190**；实际总额仍为 null，
未解决计费项仍为 1，阻断继续保持。原 campaign 文件 hash 未变。
这是显示/聚合修复，不是退款、结算或修改账单。
见 [费用修复](cost-aggregation.md) 与 [只读复核](cost-aggregation-r3-read-only.json)。

## 运行与剩余边界

本地 preview 已更新且健康；队列空闲，整份账本更新前后内容相同，仍为
`billing_review_required` / `dispatch_blocked=true`。
[服务更新凭据](preview-refresh.json)。

当前 scope 只支持既有 s1/s3/s4 源码约束及完成的原始 baseline。
任意项目、OOM/变换参照、自动生成新边界实验等仍不在已实现范围。
记录比较的是声明绑定的字段；host driver、GPU clocks、动态空闲显存和
背景负载未构成完整运行环境指纹。查询来自调用方，不是自动采集新机器的证明。
即使查询匹配，也只描述历史观察，不保证未来执行。

原 nanoGPT/s7 自动修复、整体 6/9 门槛、后续大评测/消融与比赛完整验收
仍未完成。新增付费验证仍受未解决账单限制；公网部署继续按你的决定延后。
