# Runtime patch refinement implementation — offline verification

A candidate Python implementation error can now refine a previously valid-ready diagnosis inside the original six-round loop. The prior diagnosis is reused only after its retained source/evidence/settings fingerprint matches and the current validator independently accepts it. The next candidate is generated by a fresh Super request against the reverted retained source, with the failed patch and source-bound traceback supplied as bounded context.

This implements the approved proposal without changing its historical files. It does not claim a new live repair, a GPU verification result, or an increase to the fixed-nine score or six-of-nine threshold.

## Implemented boundary

- The eligible prior candidate must be a finalized, cleanly exported and cleaned-up Python implementation error. OOM, timeout, CUDA RuntimeError, completed changed-loss candidates, numerical/parameter-policy failure, preparation failures, missing PID, and cleanup failures use the normal diagnosis path.
- The retained source file set, retained evidence, invocation/settings, policy, reference configuration, and selected run identity are fingerprinted. Unsupported trees, malformed manifests, changed source/evidence/settings, or a current validator rejection invalidate optional reuse.
- The bad candidate is reverted before the next loop. A fresh Super request generates a new patch from the retained original source. No old model patch is applied as a fresh response.
- Reuse emits a separate diagnose.reused_for_patch_refinement event and records the original diagnosis round/path/SHA with new_diagnosis_request=False. Invalidated reuse emits its own event. No new diagnose.started event or Ultra transport request is fabricated.
- The original max-rounds, model-budget hooks, patch validation, reference preflight, GPU execution, numerical checks, policy checks, speed/target checks, and keep/revert decisions remain in place. Refinement consumes an ordinary round.
- Failed-patch and source-bound traceback context is bounded to 8 KiB and included inside the existing combined 64 KiB solver limit. A context preflight failure falls back to normal diagnosis instead of increasing the cap. Arbitrary host paths, logs, and environment values are not read.

## Verification

The guarded offline run passed **147 tests in 15.56 seconds**. Ruff, Ruff format check, and git diff whitespace checks also passed. verification-final.json records commands, elapsed time, final file SHA-256 values, and confirms that all nine implementation/test/fixture files were unchanged during the checks.

The added tests use HTTP MockTransport and a synthetic Lab. They prove one Ultra request followed by two fresh Super requests, retained-source rollback before the second patch, truthful diagnosis-reuse provenance, current-validator rejection, source/evidence mismatch, numerical and policy refusal, cleanup failure, exactly six rounds, the unchanged budget hook, bounded diff/trace context, and fail-closed total context limits. These are offline control-flow results only. No provider calls, GPU work, deployment, or commit was performed by this verification.

An initial integrated run found four failures because the Store event allowlist did not recognize the two new event names. That run is preserved in focused-initial.log; the allowlist was then updated only for those names. The current checks include Store compatibility.

A broader old test had an outdated expectation that a nonempty blocked diagnosis made only one Ultra request. Before changing the assertion, the same test was run against the exact pre-feature 964b658 orchestrator in an isolated report module. It also made two requests because its existing bounded prerequisite-review mechanism was already active. The original module, exact SHA, result, and test are preserved in baseline-orchestrator-964b658.py.txt, baseline-review-attribution.json, and test_baseline_attribution.py. The updated test still requires one round, no patch, no verification, unchanged source, and needs-human status; it now checks the existing bounded review explicitly.

## Product event compatibility

The backend SSE emitter accepts the two named events. The frontend originally had a finite listener list and would ignore the new names while continuing to handle existing patch and verification events; it did not reject the stream. This was reported to root, which owns and has supplied the web labels/listener changes. Those web files are outside this implementation's ownership.
